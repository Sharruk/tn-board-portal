1. PROJECT OVERVIEW
==============================================================================

WHAT IS THIS APPLICATION?
--------------------------
The TN State Board Portal is a web-based educational resource management
platform built for Tamil Nadu State Board students of Classes 9 to 12. It
provides a structured, searchable repository of previous year question papers
and answer keys, organized by class, subject, and exam type.

WHAT PROBLEM DOES IT SOLVE?
-----------------------------
Students preparing for Tamil Nadu State Board exams traditionally struggle to
find organized, reliable previous year question papers. This portal centralizes
all academic materials in one place, removing the need to search across
multiple websites or ask seniors for physical copies.

WHO ARE THE TARGET USERS?
--------------------------
- Primary: Tamil Nadu State Board students (Classes 9, 10, 11, 12)
- Secondary: Teachers and faculty for reference
- Admin: School/institution staff who manage uploads

MAIN PURPOSE:
- Provide a single source of truth for TN State Board question papers
- Enable organized browsing by Class → Subject → Exam Type
- Allow admins to upload and manage materials efficiently

KEY BENEFITS FOR STUDENTS:
- Browse papers by class, subject, and exact exam type
- Download PDFs and documents instantly
- Like/dislike papers and comment for community feedback
- Search across all uploaded materials

KEY BENEFITS FOR FACULTY / ADMIN:
- Simple upload interface with metadata tagging
- Toggle file visibility without deleting
- Moderate and delete user comments
- Central admin dashboard for all management tasks

6. DATABASE / STORAGE ANALYSIS
==============================================================================

--- POSTGRESQL DATABASE (PRIMARY) ---

TABLE: subjects
  - id           : Integer, Primary Key
  - code         : String(20), unique — subject slug (e.g. "physics", "maths")
  - name         : String(200) — display name (e.g. "Physics")
  - class_level  : String(10) — "9", "10", "11", "12"
  - category     : String(50) — "Theory" or "Practical"
  - created_at   : DateTime
  - updated_at   : DateTime
  Seeded with 24 subjects by init_db.py (6 per class level)

TABLE: files
  - id               : Integer, Primary Key
  - filename         : String(255) — stored filename (with timestamp prefix)
  - original_filename: String(255) — original uploaded name
  - custom_filename  : String(255) — admin-chosen display name
  - class_level      : String(10) — "9"/"10"/"11"/"12"
  - subject_id       : Integer, FK → subjects.id (nullable)
  - subject_name     : String(200) — denormalized subject name for fast lookup
  - exam_type        : String(100) — e.g. "Unit Test 1", "Annual Exam"
  - year             : String(10) — e.g. "2024"
  - description      : Text (optional)
  - file_path        : String(500) — full path to physical file
  - size             : String(50) — human-readable size ("1.2 MB")
  - upload_date      : DateTime
  - visible          : Boolean (default True)
  - likes            : Integer (default 0)
  - dislikes         : Integer (default 0)

TABLE: comments
  - id          : Integer, Primary Key
  - file_id     : Integer, FK → files.id
  - author_name : String(80)
  - content     : Text
  - created_at  : DateTime

TABLE: users
  - id            : Integer, Primary Key
  - username      : String(80), unique
  - email         : String(120), unique
  - password_hash : String(255) — Werkzeug hashed password
  - is_admin      : Boolean
  - created_at    : DateTime

RELATIONSHIPS:
  Subject  1──* File     (Subject has many Files)
  File     1──* Comment  (File has many Comments)

--- DATA.JSON (DUAL-WRITE CACHE) ---

Structure:
{
  "classes": {
    "9": { "name": "Class 9", "subjects": { "tamil": {...}, "maths": {...} } },
    "10": { ... },
    "11": { ... },
    "12": { ... }
  },
  "files": [ { id, filename, custom_filename, class_level, subject_id,
               subject_name, exam_type, year, visible, likes, dislikes,
               size, description, upload_date, comments: [...] } ],
  "exam_categories": [ { "name": "...", "types": ["..."] } ]
}

Purpose: Fast flat-file reads for browsing routes; avoids repeated DB queries
         on every page load. Written synchronously on every upload/delete/toggle.

--- FILE SYSTEM ---

/uploads/  — Physical storage for all uploaded files
  Format: <YYYYMMDD_HHMMSS>_<secure_filename>  (e.g. 20240615_143022_physics_q.pdf)
  Purpose: Timestamp prefix prevents filename collisions

HOW UPLOAD WORKS:
  1. Admin fills upload form → POST /upload
  2. File saved to /uploads/ with timestamp prefix
  3. File record inserted into PostgreSQL (files table)
  4. data.json updated with file's to_dict() output

HOW DELETE WORKS:
  1. Admin clicks delete → POST /admin/delete-file/<id>
  2. Physical file removed from /uploads/ (if exists)
  3. Record deleted from PostgreSQL
  4. File entry removed from data.json['files']

HOW RETRIEVAL WORKS:
  - Browse routes read data.json for speed
  - Admin manage-files reads directly from PostgreSQL
  - Download serves physical file via send_from_directory

10. SECURITY ANALYSIS
==============================================================================

CURRENT MEASURES:
+ Passwords stored as Werkzeug hashed values (pbkdf2:sha256) — GOOD
+ Admin login URL is configurable via ADMIN_SECRET_PATH env var — GOOD
+ Session-based auth with Flask sessions (signed by SECRET_KEY) — GOOD
+ SECRET_KEY loaded from environment variable SESSION_SECRET — GOOD
+ secure_filename() used on all uploads — GOOD
+ File served via send_from_directory (not direct path exposure) — GOOD
+ Visibility toggle prevents public access to hidden files — GOOD

VULNERABILITIES:
! No file size limit (MAX_FILE_SIZE = None) — DOS risk via huge file upload
! ALLOWED_EXTENSIONS checked but only by extension string — no MIME type check
! mp4 video files allowed but no sanitization — potential malicious file upload
! Vote API (/api/vote) has no rate limiting — vote stuffing possible
! Comment API (/api/comment) has no rate limiting or spam protection
! No CSRF protection on admin POST forms
! Admin logout is GET not POST — CSRF possible on logout
! session.permanent not set — session lifespan undefined
! No brute-force protection on admin login (unlimited attempts)
! data.json path traversal: os.path.exists used but no sandboxing of file paths

CURRENT SECURITY SCORE: 5.5 / 10

PRIORITY IMPROVEMENTS:
1. [HIGH]   Add MAX_CONTENT_LENGTH to limit upload size (e.g., 50MB)
2. [HIGH]   Add CSRF protection (Flask-WTF or manual token)
3. [HIGH]   Validate MIME type in addition to file extension
4. [HIGH]   Rate-limit vote and comment endpoints
5. [MEDIUM] Add login attempt throttling / lockout after N failures
6. [MEDIUM] Change admin logout to POST request
7. [LOW]    Set session.permanent = True with a defined lifetime

11. PERFORMANCE ANALYSIS
==============================================================================

SCALABILITY:
- File browsing reads data.json on every request — this is fast for small
  datasets (<500 files) but will become a bottleneck at scale
- data.json is a flat list; filtering is O(n) on every page load
- PostgreSQL is the right foundation — but most browse routes bypass it
  in favor of JSON, reducing DB benefits

STORAGE EFFICIENCY:
- Dual-write (DB + JSON) means data is duplicated; risk of drift if one write
  fails mid-operation (no transaction wrapping both)
- Files stored in /uploads/ with no chunking or CDN — local disk only
- No deduplication; same file can be uploaded twice with different names

FILE HANDLING PERFORMANCE:
- send_from_directory is Flask's built-in file serving — acceptable for
  moderate traffic but not production-CDN-grade
- No streaming for large files (entire file loaded into memory)

BOTTLENECKS:
1. data.json read + parse on every browsing request (no in-memory cache)
2. No database indexes defined on commonly-queried columns (class_level,
   subject_id, exam_type)
3. No query-level pagination — all files loaded for a category at once
4. Admin manage-files loads ALL files — no pagination

DATABASE READINESS:
- Schema is well-designed and production-ready
- Missing: indexes on File.class_level, File.subject_id, File.visible
- Missing: composite index on (class_level, subject_id, exam_type)

"EXPLAIN YOUR PROJECT" ANSWER (1 MINUTE):
------------------------------------------
"I built a web portal for Tamil Nadu State Board students to access previous
year question papers. Students can navigate by their class — 9, 10, 11, or 12
— then choose a subject like Physics or Maths, then pick the exam type like
Unit Test or Annual Exam, and download the paper. The backend is Python Flask

files and manage content. The UI is built with Bootstrap 5 and is fully
responsive. It's deployed on Replit with Gunicorn as the production server."

TECHNICAL ARCHITECTURE ANSWER:
--------------------------------
"The architecture uses Flask as the web framework with SQLAlchemy ORM connecting
to PostgreSQL. I implemented a dual-storage pattern: every file upload writes
metadata to both PostgreSQL (for structured queries and relational data) and a
JSON file (for fast flat reads on browse pages). The browsing routes read from
JSON for performance, while admin routes query the database directly. File
storage is on the local filesystem in an /uploads/ directory with timestamp
prefixes to prevent collisions. Admin authentication uses Flask sessions signed
with a secret key, with passwords stored as Werkzeug PBKDF2 hashes."

CHALLENGES FACED ANSWER:
--------------------------
"One interesting challenge was the dual-storage consistency problem. When a file
is uploaded or deleted, I need to update both PostgreSQL and data.json. If one
write fails, the data gets out of sync. I solved this by ordering the operations
— commit to database first, then update JSON — and wrapping them in try/except
blocks with rollback. Another challenge was the exam category UX: I wanted
students to see all possible exam types even if no files exist yet, but without
making them dead links. I designed 'Coming soon' cards that look distinct and
are non-clickable when a category has no files."

FUTURE IMPROVEMENTS ANSWER:
-----------------------------
"The highest priority improvement is replacing the client-side search with
server-side PostgreSQL full-text search using ILIKE queries — the current
search can only find files already rendered on the page. I'd also add file size
limits (currently unlimited), CSRF protection on admin forms, and rate limiting
on the voting API to prevent abuse. Longer term, I'd migrate file storage to
AWS S3 or Cloudinary for scalability, add student accounts with saved favorites,
and build an analytics dashboard showing download counts and popular papers."
