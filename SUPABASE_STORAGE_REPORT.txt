====================================================
SECTION 1 — OVERVIEW
====================================================

Supabase Storage is now the active file storage backend for the
TN State Board Learning Platform. Uploaded PDFs are stored in a
Supabase Storage bucket and served via Supabase's global CDN,
replacing the ephemeral local filesystem (uploads/).

No frontend code was changed. All admin upload APIs work identically.
Existing papers with local file_path values remain readable (local
provider still exists and still works if STORAGE_BACKEND=local).

====================================================

====================================================

Bucket configuration in Supabase dashboard:
  Bucket name: papers

====================================================
SECTION 4 — HOW IT WORKS
====================================================

UPLOAD FLOW
-----------
  1. Admin POSTs multipart form to POST /api/v1/admin/papers
  2. admin.py calls save_file_locally(file) (name unchanged)
  3. save_file_locally() calls validate_file() then _provider.save()
  4. SupabaseStorageProvider.save():
       a. Reads file bytes into memory
       b. Validates size ≤ MAX_FILE_SIZE_MB (50 MB)
       c. Generates: stored_filename = uuid4().hex + ".pdf"
       d. Calls: supabase.storage.from_("papers").upload(...)
       e. Gets:  public_url = supabase.storage.from_("papers").get_public_url(...)
       f. Returns (stored_filename, public_url)
  5. admin.py stores:
       paper.file_path  = stored_filename   (UUID, used for deletion)
       paper.public_url = public_url        (CDN URL, used for viewing)
  6. paper row committed to PostgreSQL

DOWNLOAD FLOW (unchanged)
--------------------------
  Students click the public_url stored in the DB.
  The URL is a direct Supabase CDN link:
    https://<project>.supabase.co/storage/v1/object/public/papers/<uuid>.pdf
  No proxy through FastAPI — file served directly by Supabase CDN.

DELETE FLOW
-----------
  1. Admin calls DELETE /api/v1/admin/papers/{id}
  2. admin.py reads paper.file_path (the UUID filename)
  3. DB row is deleted first (always succeeds)
  4. delete_file_locally(paper.file_path) called
  5. SupabaseStorageProvider.delete():
       Calls: supabase.storage.from_("papers").remove([stored_filename])
       Logs success or warning (never raises, so DB op is never rolled back)

EDIT FLOW (unchanged)
----------------------
  PUT /api/v1/admin/papers/{id} modifies metadata only (title, year,
  exam_type, youtube_url, is_visible). No file is re-uploaded on edit.
  file_path and public_url remain unchanged.

====================================================
SECTION 6 — BACKWARD COMPATIBILITY
====================================================

Papers uploaded before this change (with file_path = local path):
  - Their public_url is "/uploads/<filename>" (relative)
  - The FastAPI /uploads/ StaticFiles mount still serves them in dev
  - In production these files will not survive redeployment (this was
    always the case with local storage)
  - Solution: Re-upload any existing papers through the admin panel

Provider switching:
  Setting STORAGE_BACKEND=local reverts to the local filesystem.
  Setting STORAGE_BACKEND=supabase (current) uses Supabase.
  Both providers implement the same interface — admin.py is unaffected.

API contract:
  POST /api/v1/admin/papers   — response shape unchanged
  PUT  /api/v1/admin/papers/{id} — unchanged
  DELETE /api/v1/admin/papers/{id} — unchanged
  All public paper endpoints — unchanged

SECTION 8 — REMAINING DEPLOYMENT NOTES
====================================================

1. The `papers` Supabase bucket must remain PUBLIC for student
   download links (public_url) to work without authentication.

2. SUPABASE_SERVICE_ROLE_KEY grants full storage access.
   Confirm it is stored in Replit Secrets (not shared env vars).

3. The local `uploads/` directory is now unused for new uploads
   but is kept in the repo (with .gitkeep) for backward compat.

4. In-memory pydantic version was upgraded by supabase SDK
   (pydantic 2.9.2 → 2.13.4). All existing schemas remain compatible
   — no API behaviour changes observed.
